# ADR-003: Durable Post-Commit Alert Evaluation and Replay Semantics

## Status
Accepted

## Date
2026-10-05

## Context
In Phase 3 of the TikTok Shop Affiliate Trend Hunter, we introduce product-scoped Watchlists and Alert Rules (`sales_velocity_above`, `trend_score_above`, `price_change_pct`).

The application is a single-node desktop system running on local SQLite and FastAPI. It must reliably evaluate alert conditions across periodic crawls and manual product additions without:
1. Coupling ingestion reliability to alert evaluation failures.
2. Generating duplicate alerts or missing alerts across application crashes or restarts.
3. Introducing heavyweight external infrastructure such as Redis, RabbitMQ, Kafka, or Celery.
4. Distorting historical or baseline data through retroactive alerting.

## Decision

### 1. Ingestion is Authoritative
`ProductSnapshot` commits are the authoritative, primary source of product history. Alert evaluation is never nested inside or coupled with the ingestion transaction. If an alert evaluation encounters an exception, the ingestion remains committed and uncorrupted.

### 2. Post-Commit Evaluation in Isolated Transaction
Alert evaluation runs in a strictly separate database transaction after the ingestion transaction has committed. If the alert transaction fails, it rolls back cleanly and leaves the rule cursor behind for subsequent retry.

### 3. At-Least-Once Evaluation with Exactly-Once Durable Event Effect
- **At-Least-Once Replay**: Active rules maintain a durable cursor `last_evaluated_snapshot_id`. Any snapshots committed with `id > last_evaluated_snapshot_id` are processed in strict chronological order during crawls or startup catch-up.
- **Exactly-Once Event Persistence**: The `alert_events` table enforces a composite database uniqueness constraint:
  ```sql
  UNIQUE(rule_id, triggering_snapshot_id)
  ```
  If a crash occurs during evaluation, re-evaluating the same snapshot cannot produce duplicate events.

### 4. Atomic Event, Cursor, Condition, and Cooldown Advancement
Inserting an `AlertEvent`, advancing `last_evaluated_snapshot_id`, updating `last_condition_met`, and recording `last_triggered_at` are executed within a single atomic database commit. They succeed together or fail together.

### 5. Deterministic Edge Crossing and Cooldown Semantics
- **Edge Crossing**: An alert is eligible to trigger only on a `False -> True` condition transition, or on subsequent qualifying snapshots when not suppressed by cooldown.
- **Cooldown**: Default duration is 0 minutes. Suppression occurs strictly when:
  ```
  trigger_time - last_triggered_at < cooldown_duration
  ```
  Snapshots evaluated exactly at or after the cooldown boundary are eligible. A suppressed crossing still advances `last_condition_met = True`. Cooldown expiration alone never emits a delayed event without a new triggering snapshot.

### 6. Strict Price Rule Semantics
- Direction is explicitly validated: `direction ∈ {'up', 'down', 'either'}`.
- Threshold must be strictly positive (`threshold > 0`).
- Percentage change calculation requires strictly positive, non-null current and previous prices:
  ```
  pct_change = (current_price - previous_price) / previous_price * 100
  ```
- Evaluated conditions:
  - `up`: `pct_change >= threshold`
  - `down`: `-pct_change >= threshold`
  - `either`: `abs(pct_change) >= threshold`
- The emitted `AlertEvent` persists `actual_direction` (`up` or `down`).
- Price alerts are explicitly formatted as price movements and must never be described as "trending".

### 7. Deterministic As-Of Analytics Reuse
Replayed alert evaluation reuses the Phase 2 Trend Engine deterministically as-of the triggering snapshot's timestamp (`captured_at`), strictly bounded to 172 hours and excluding any future snapshots. Analytics are computed once per (product, triggering snapshot) and shared across all active rules for that product.

### 8. No Retroactive Rule Baseline Alerts
When an alert rule is created, updated, or re-enabled, its condition baseline is initialized against the latest existing snapshot (if any). It seeds `last_evaluated_snapshot_id` and initial condition state without firing retroactive alerts on historical data.

### 9. Synchronous Startup Catch-Up and Readiness Ordering
Application startup executes synchronously in the following strict order:
1. Database schema, bootstrap, and legacy tracked backfill.
2. Crawl run reconciliation (recovering interrupted runs).
3. Alert catch-up worker (processing un-evaluated snapshots for all active rules).
4. Scheduler start.
5. Application ready (FastAPI serving requests).

Catch-up failure halts application startup and prevents scheduler initialization, eliminating silent replay gaps.

### 10. Single-Node Desktop Architectural Constraints
The architecture explicitly rejects:
- Secondary background schedulers or polling threads.
- In-memory or external brokers: No Redis, No Memcached.
- External messaging queues: No RabbitMQ, No Kafka, No SQS.
- Distributed background workers: No Celery, No RQ.

All durability and coordination rely on transactional SQLite with WAL mode.

## Rejected Alternatives & Trade-Offs

| Alternative | Reason Rejected |
| :--- | :--- |
| **Ingestion-Coupled Transaction** | Alert evaluation errors could abort valid web crawl ingestion, causing data loss and network waste. |
| **Redis / Celery Queue Worker** | Adds heavyweight external dependencies unsuitable for a self-contained local desktop application; introduces state divergence if queue crashes. |
| **Interval-Based Polling Evaluator** | Scanning entire history on a cron wastes CPU/IO and fails to guarantee deterministic as-of snapshot alignment. |
| **Retroactive Alerting on Rule Creation** | Generates an immediate cascade of stale notifications for events that occurred weeks or months in the past. |

## Consequences
- **Positive**: Complete fault tolerance and idempotent recovery on local SQLite. Ingestion latency is completely unburdened by alert evaluation. Zero replay gaps across process restarts or crashes.
- **Negative / Trade-off**: Replay catch-up on application startup runs synchronously, which adds a brief deterministic catch-up step if the application was stopped for an extended period with many crawls.
