# ADR-004: Local Backup/Restore Integrity, Keyset Streaming CSV Exports, and Compatibility Semantics

## Status
Accepted

## Date
2026-10-05

## Context
In Phase 4 of the TikTok Shop Affiliate Trend Hunter, we introduce data portability (deterministic CSV exports), system durability (hot SQLite backup and offline restore), and operational diagnostics.

The system is a local desktop application running FastAPI on port 8000 and Next.js on port 3000 on Windows. It uses a single SQLite file (`backend/affiliate.db`) with `journal_mode=delete`.

Key constraints and risks:
1. **Windows File Locking (`WinError 32`)**: Active connection handles in SQLAlchemy's connection pool lock the SQLite file on Windows. Live in-process database replacement is unsafe and fails with file-locking errors.
2. **Export Membership Drift & Transaction Bloat**: Streaming large historical snapshot or event datasets over slow network connections must not hold a long-running SQLite read transaction that starves background crawler writers. Membership must not drift or include post-start backdated records.
3. **Data Security & Portable Boundaries**: TikTok Shop browser session cookies and tokens (`backend/.local/tiktok-session.json`) must remain host-bound and strictly excluded from portable backups.
4. **Foreign Key Enforcement**: SQLite connections default to `PRAGMA foreign_keys = 0`. While existing data is 100% referentially valid, globally enabling runtime enforcement in Phase 4 risks unvetted crawl regressions and is classified as non-blocking cross-phase technical debt. However, backup and restore engines must strictly validate foreign keys.

## Decision

### 1. Portable Application Boundary & Session Exclusion
- The portable application boundary consists strictly of `backend/affiliate.db` containing the 10 authoritative tables:
  `products`, `product_snapshots`, `crawl_runs`, `categories`, `product_video_links`, `quarantined_products`, `watchlist_items`, `system_metadata`, `alert_rules`, and `alert_events`.
- TikTok authentication artifacts (`backend/.local/tiktok-session.json`, cookies, localStorage tokens) are strictly excluded from backup archives and exports.

### 2. Operator Hot SQLite Online Backup Engine (`BACKUP.bat`)
- Backups use the official Python `sqlite3.Connection.backup()` API (`pages=250, sleep=0.005`) to create point-in-time consistent copies of the active database into `backend/.local/backups/tinix-affiliate-v1-YYYYMMDDTHHMMSS.ffffffZ.sqlite3` via the operator entry point `BACKUP.bat`.
- Browser-initiated backup download is deferred to prevent exposure of database files over HTTP.
- Pre-publish validation on staging file (`.staging_tinix-affiliate-v1-*.sqlite3`): Candidate backup files must pass:
  1. SQLite magic header check (`b"SQLite format 3\x00"`).
  2. Required schema verification derived dynamically from SQLAlchemy `Base.metadata` (tables and columns).
  3. Compatibility version check (`portable_backup_compatibility_version == "1"` in `system_metadata`).
  4. `PRAGMA integrity_check == 'ok'`.
  5. `PRAGMA foreign_key_check == []`.
- Backups are atomically published only after all checks pass. File overwrite is prevented with timestamped names, microsecond resolution, and collision checks.

### 3. Compatibility Marker & Same-Version Policy
- Application startup seeds `portable_backup_compatibility_version = "1"` in `system_metadata`.
- Phase 4 enforces same-version restore compatibility. Cross-version migrations are deferred until a formal migration framework is adopted.

### 4. Offline Launcher-Owned Restore Lifecycle
- To eliminate Windows file-locking failures (`WinError 32`), restore is strictly offline and launcher-owned (`RESTORE.bat` / `scripts/restore.ps1`).
- Lifecycle stages:
  1. **Candidate Staging & Validation**: Verifies candidate file existence, SQLite header, required tables/columns via model metadata, compatibility version "1", integrity check, and foreign key check while services are still running. Rejects invalid candidates before any service disruption.
  2. **Service Quiescence**: Stops backend and frontend services using `scripts/stop_services.ps1 -Target All`, ensuring ports 8000 and 3000 are freed.
  3. **Validated Pre-Restore Safety Backup**: Creates `backend/.local/backups/tinix-pre-restore-v1-YYYYMMDDTHHMMSS.ffffffZ.sqlite3` using the validated SQLite backup engine (staging + schema, integrity, and foreign key verification before publishing). Existing safety backups are never deleted or overwritten.
  4. **Atomic Replacement**: Replaces `backend/affiliate.db` with candidate copy. Rollback is triggered immediately if replacement fails.
  5. **Startup & Reconciliation**: Starts services via `scripts/start_services.ps1 -Target All`. Standard startup runs `init_db()` (reconciling interrupted crawls) and `AlertService.catch_up_alerts()`.
  6. **Post-Restore Health Check**: Validates HTTP 200 and database connectivity. If verification fails, services are stopped and the safety backup is restored (`ROLLED_BACK`).

### 5. Restore Transaction Manifest & Pre-Start Guard
- Restore operations maintain a persistent JSON manifest: `backend/.local/restore/manifest.json`.
- Valid manifest states: `IDLE`, `VALIDATING_CANDIDATE`, `STOPPING_SERVICES`, `SAFETY_BACKUP_CREATED`, `REPLACEMENT_STARTED`, `COMPLETED`, `ROLLED_BACK`, `ABORTED`.
- Only `COMPLETED`, `ROLLED_BACK`, and `ABORTED` are terminal.
- **Pre-Start Manifest Guard**: Launcher scripts (`start_services.ps1` and `RESTART.bat`) inspect `backend/.local/restore/manifest.json` before starting services. Any non-terminal state blocks normal startup with an explicit operator instruction.
- **Recovery Mode (`RESTORE.bat --recover`)**:
  - Pre-replacement interruptions recover safely to `ABORTED`.
  - At/after `REPLACEMENT_STARTED`, recovery verifies replacement and health or reverts to the safety backup, reaching `COMPLETED` or `ROLLED_BACK`.

### 6. Keyset Streaming CSV Exports & Membership Freeze
- **Product History Export (`GET /api/products/{id}/export-history`)**:
  - Supports exactly `24h`, `7d`, `30d`. `Tất cả` is viewable in UI but rejected for export with structured 400.
  - Freezes membership at request start using `as_of_utc`, derived lower bound, and `max_snapshot_id_at_start`.
  - Keyset pagination order: `(captured_at, snapshot_id) ASC`.
  - Excludes higher-ID snapshots created after request start even if timestamps are backdated.
- **Alert History Export (`GET /api/alerts/events/export`)**:
  - Freezes membership using `max_event_id_at_start`.
  - Keyset pagination order: `(created_at, event_id) DESC`.
  - Excludes higher-ID events created after request start even if timestamps are backdated.
- **Trends & Watchlist Exports**:
  - Reuses authoritative Phase 2 (`TrendService`) and Phase 3 (`WatchlistService`) query logic.
  - Exports exactly the active displayed query result set including filter parameters and pagination limit/offset. Does not silently dump all rows.
  - Avoids adding per-row metadata queries to Watchlist merely for `watched_at` or `notes`.
- **Short-Lived Sessions & Batch Granularity**:
  - Streaming generators acquire short-lived database sessions per batch (batch size 1000) and close them immediately. No database transaction spans the entire HTTP streaming download.
- **UTF-8 BOM (`\ufeff`)**:
  - All CSV streams include the UTF-8 BOM (`utf-8-sig`) to ensure Vietnamese diacritics render correctly in Microsoft Excel on Windows.

### 7. Runtime Foreign Key Posture
- Runtime database connections continue with standard SQLite default (`PRAGMA foreign_keys = 0`).
- Enabling runtime foreign key enforcement globally is classified as non-blocking pre-existing technical debt, deferred to Project Control for cross-phase regression testing.
- Backup validation, candidate restore validation, and deep diagnostics strictly execute `PRAGMA foreign_key_check`.

### 8. System Diagnostics Security
- System diagnostics (`GET /api/diagnostics`) are strictly allowlisted and local.
- Diagnostic payloads report table row counts, DB file size, scheduler jobs, crawl status, and session availability enum (`available` / `missing` / `invalid`).
- Redaction guarantee: Cookies, localStorage, credentials, auth headers, and arbitrary filesystem paths are never exposed.
- Deep integrity checks (`PRAGMA integrity_check`, `PRAGMA foreign_key_check`) run only via explicit operator action (`GET /api/diagnostics/deep`), never automatically on page view.

## Consequences
- **Positive**: Eliminates risk of Windows file locking during backup or restore. Guarantees zero export membership drift or transaction lock contention. Prevents credential leakage. Provides reliable disaster recovery.
- **Negative / Trade-off**: Database restore requires brief offline service quiescence. Exporting very large snapshots relies on keyset iteration across multiple short-lived queries rather than a single database cursor.
