# ADR-006: TikTok Content Signals and Video Association

## Status

Accepted — 2026-10-07. Independent review and implementation authorization are recorded in [`PROJECT_CONTROL_PHASE7_PACKAGE_APPROVED.md`](../../PROJECT_CONTROL_PHASE7_PACKAGE_APPROVED.md).

## Context

Phase 7 adds operator-curated public video links to the local product research workflow. TikTok's documented oEmbed endpoint supports embed metadata, while its documented Research and Display APIs do not provide an unrestricted commercial endpoint for arbitrary creators' video metrics. Public page markup may expose additional fields, but its shape and availability are undocumented and can change.

The project already has `ProductVideoLink`, a product-to-external-video association. The earlier proposal stored snapshots against a per-product association, duplicating identity and history for one video linked to multiple products. It also proposed browser fallback when a challenge appears, contrary to the repository's no-bypass rule.

## Decisions

1. **Curated associations.** An operator submits a TikTok video URL for a product. Phase 7 does not perform broad search, infer product attribution, or harvest showcase links automatically. Association source is recorded using the existing mapping model.
2. **Conservative retrieval.** Refresh is explicit and on demand. Prefer documented public metadata such as oEmbed where appropriate. An optional parser for ordinary, successful public video-page responses may be used only as a best-effort, schema-variant source. Its fields are nullable and are never represented as a stable TikTok API contract.
3. **Challenge stop boundary.** Do not use authenticated session cookies, Playwright fallback, retries of challenges, CAPTCHA solvers, stealth, signature generation, or other challenge bypasses. Stop on 403/429, challenge/interstitial content, redirects outside the allowlist, or an unsupported response. Store a bounded status/error classification, not challenge HTML or credentials. A failed refresh creates no metric snapshot.
4. **Global identity and durable history.** Add `tiktok_videos`, keyed by canonical numeric `video_id` (text), for shared metadata, and `video_snapshots`, keyed by an integer observation ID with `video_id` referencing the global entity. Reuse `ProductVideoLink` for product association; its existing `external_video_id` must match a row in `tiktok_videos`, enforced by the service because the legacy column has no foreign key. A video's metadata and metric history are shared if linked to multiple products. Detaching a product association deletes only that association; it does not cascade-delete video identity or snapshots. Product deletion may cascade its association rows while retaining global observations. Video identity deletion is not exposed; the snapshot FK restricts deletion.
5. **Honest observations.** Store only values actually present in a successful response, with capture time and source. `view_count`, `like_count`, `comment_count`, `share_count`, and `collect_count` are individually nullable. Missing values remain null. Do not copy an old metric into a new snapshot. Per-metric velocity is null unless two non-null observations exist with the prior capture 20–28 hours before the latest capture; divide by actual elapsed time. Decreases retain both observations and are represented as anomalies rather than silently rewriting history.
6. **Domain separation.** Content signals do not change Phase 2 sales Trend Score, evidence confidence, trend state, alerts, crawl scheduling, or Phase 6 economics. Any blended score is a later decision.
7. **Local data boundary.** No video/audio binaries, credentials, or raw page bodies are persisted. Thumbnail URLs are validated public HTTPS URLs and rendered safely. Content operations remain local and use existing backup/restore mechanisms.
8. **Compatibility and recovery.** Adding application tables advances portable backup compatibility from `"3"` to `"4"` under ADR-004. Existing same-version restore rules remain authoritative. Test additive bootstrap, v4 backup, and deterministic rejection of older versions before release.
9. **Bounded work.** No scheduled/bulk refresh in this phase. Rate and concurrency are bounded; user action initiates one refresh. A challenge is not retried automatically.

### Additive tables

- `tiktok_videos`: `video_id` (canonical text primary key), canonical URL, nullable creator handle/nickname, description, public thumbnail URL, nullable publication time, created/updated timestamps.
- `video_snapshots`: integer primary key, `video_id` foreign key to `tiktok_videos.video_id` with delete restriction, nullable public counters listed above, capture timestamp, source identifier, and bounded availability/status classification. Index by `(video_id, captured_at DESC)`.

Bootstrap adds these tables without altering `product_video_links`. The service creates/resolves the global video row before linking it. Snapshot history is immutable.

## Consequences

- The feature can persist and organize links even when TikTok supplies no metrics.
- Metrics may be unavailable and may disappear as page formats change. The UI must make source and refresh outcome visible.
- There is no guaranteed arbitrary-video metrics API in this scope; future access requiring an approved research project or user authorization requires a separate product decision.
- Shared video identity prevents duplicated observation history and preserves it after a product is unlinked.
- Compatibility advances to `"4"` only with the implemented schema.

## Review requirements

The independent architecture review must verify official API boundaries, challenge handling, association reuse, global identity semantics, backup compatibility, and that the proposal introduces no authentication or challenge-bypass path.
